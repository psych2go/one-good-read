## Public health contract

Both endpoints are read-only, `Cache-Control: no-store`, and catch D1 failures as safe **503** responses. Neither retrieves R2 bodies nor calls AI, source websites, email, or Workflow APIs.

- `/health/live`: D1 `SELECT 1` liveness only, not publication health.
- `/health`: retains `ok`, Shanghai `date`, `analysisVersion`, `selectionVersion`, and `automationEnabled`; adds typed overall/component statuses, fixed reason codes, current visible public date, expected publication date, query timestamp, and check timestamps. No alert bodies, candidate metadata, emails, stack traces, or persisted diagnostic strings are returned.
- Before **06:00 Asia/Shanghai**, yesterday's visible, non-withdrawn recommendation is expected. Today's future-visible row does not count. Between **06:00 inclusive and 06:30 exclusive**, a missing today is an explicit `grace` / overall `warning` (200 if other components are healthy). At **06:30**, missing today's visible recommendation is 503, even if D1 and the homepage are reachable.
- Before **07:00**, a completed check started at or after yesterday's 06:30 is required. At **07:00**, one started at or after today's 06:30 is required. Missing/corrupt/stale/failed heartbeats fail closed with 503; there is no indefinite first-install healthy grace.
- `running` is not a successful check. A running attempt may be overall warning/200 only before 07:00, for less than ten minutes, with a sufficiently recent prior all-components-healthy success. Otherwise it is 503. A newly completed check can diagnose an unhealthy publication/storage condition: completion alone does not imply business health.
- Cleanup errors and critical tracked-storage pressure make business health unhealthy. Storage warning or a remaining bounded cleanup backlog is warning. Storage figures come from the existing D1 tracked-object ledger, not a full live R2 inventory/reachability probe. Public reads observe only stored cleanup/storage results.
- With public automation off, publication/monitor/cleanup/storage expectations are explicitly `disabled`, not overdue. Readable D1 yields `ok=true,status=disabled`; D1 failure still yields 503.

## Durable monitoring, not the publication critical path

The existing **06:30 Shanghai** cron launches `BACKFILL_WORKFLOW` with `{healthCheck:true}` and stable `health-DATE` ID via the existing idempotent `createBatch` helper. This depends on `AUTOMATION_ENABLED`, **not** `BACKFILL_ENABLED`. It adds neither a Workflow service nor a fifth cron. The health branch executes before the backfill storage guard and all ingestion. Publication remains independent.

One Workflow step has a ten-minute timeout and two retries with one-minute exponential delay. Every attempt records a real `running` start before work. Publication, bounded cleanup (100 objects), and tracked storage are diagnosed independently; a cleanup exception does not suppress publication diagnosis. Thrown I/O failures are recorded as failed if D1 is available and rethrown for Workflow retry. If D1 cannot record the failure, the previous running/missing state fails closed and the Workflow still fails/retries. Worker termination cannot manufacture completion.

`system_state.operational_health` holds the latest attempt ID, started/completed/failed timestamps, status, component results and private diagnostics. Completion/failure writes cannot overwrite a newer attempt ID. Incident creation/repetition/recovery and timestamp writes atomically check that same current attempt ID inside SQL: an older healthy result cannot close a newer incident, and an older unhealthy result cannot reopen or repeat an incident after a newer healthy check. Separate monotonic `operational_health_completed`, `operational_health_failed`, and `operational_health_success` timestamp entries retain the last completed, failed and all-components-healthy observations across later attempts. Missing publication or storage pressure can be a completed diagnosis without an all-healthy success timestamp. The state is monitoring evidence, not permission to publish or rewrite history.

The Access-protected admin **运行健康检查 / 初始化监控** button POSTs `/admin/run-health-check`, using the same Workflow health payload with a unique manual ID. It respects public automation disable. It performs no synchronous health work or fabricated heartbeat write. New health/acknowledgement controls additionally require an explicit same-origin `Origin` header; existing Access middleware validates authorization and rejects foreign origins. Existing unrelated controls retain their prior origin behavior.

## Alert episodes and delivery

Migration **0013_alert_lifecycle.sql** is additive. Original alert fields and rows are unchanged. New columns are lifecycle status, last-seen/count, acknowledgement/resolution timestamps and managed condition. The default is **historical**, meaning unknown recovery, not resolved. Old Worker inserts after migration remain compatible and historical. No migration updates/bulk resolutions occur.

New alerts explicitly open an episode. A SQLite partial unique index allows one `open` or `acknowledged` episode per dedupe key. A single `INSERT ... ON CONFLICT ... RETURNING` atomically creates it or increments last-seen/count and updates the current severity/message. Only the creator attempts notification, **after** persistence. A send interruption leaves a durable `logged` record; a caught send error leaves the original incident with `delivery_status=failed`. Repeats do not send again, including after acknowledgement. Resolution allows a later recurrence to create a new ID/episode.

- Acknowledgement is same-origin authenticated `POST /admin/alerts/:id/acknowledge`. It is idempotent, never resolves, and preserves acknowledgement on recurrence within the unresolved episode. Unknown IDs return 404; resolved/historical IDs return 409. No manual resolve control is supplied.
- Only health-managed conditions auto-resolve on actual healthy observation: `health:storage`, `health:cleanup`, and `health:publication:DATE`. Cleanup does not resolve while overdue objects remain beyond the bounded batch.
- Publication keys are deliberately date-specific. Today's visible publication resolves only today's matching managed episode, **not** a prior missing date. Old `missing-publication:DATE`, source, selection, simulation, backfill and historical alerts are not silently resolved. Past managed publication episodes remain unresolved absent an actual check of that date; this slice supplies no retroactive repair/resolve tool.
- Admin lists at most 100 episodes, unresolved first, grouped into open / acknowledged / resolved / historical; it shows first/last seen, count, acknowledgement/recovery timestamps, private details and delivery status. The limit is explicit, so a group is not an exhaustive history/count.
- Delivery readiness is `disabled`, `misconfigured`, or `ready`. `ready` means only that enabled/to/from and the existing optional EMAIL interface are present; it is **not** verified delivery. Misconfiguration is recorded as failed, disabled delivery as disabled. No provider/binding/domain onboarding or configuration activation occurs here. Real domain setup, send verification, notification retries and circuit breaker remain deferred. Enabling email later does not replay old/disabled/logged episodes automatically.

## Blind-spot remediation — 2026-09-19

A twelve-day production review found the monitoring design healthy while the AI relay had been failing since 2026-09-13: analyses stopped (0 successes in 6 days), and the last four published cards used the outage fallback copy. No alert fired because (a) `backfill_stalled`/`reservoir_stale` are suppressed when the ready pool is at or above the reservoir target, (b) `analysis_failure_rate` used the all-time ratio (35/720 = 4.9%), which a multi-day outage cannot move, (c) editor-choice and copywriting fallbacks only logged to `console.error`, and (d) publication kept succeeding through fallbacks so every `selection_run` stayed `complete`. Changes:

- **Degraded selection runs**: a run that publishes through `editor_choice_fallback` and/or `copywriting_fallback` is now marked `degraded` with the reasons in `failure_reason`, and raises a `selection_degraded` alert (`warning` on the first day, `critical` once consecutive).
- **Windowed failure detection**: `analysis_failure_window` alerts when the last 24 hours processed ≥5 articles with ≥50% `analysis_failed`. Independent of the reservoir target.
- **Stall detection**: `analysis_stalled` (critical) alerts when no analysis succeeded in 48 hours while work is pending (`discovered`/`analysis_failed` backlog), also independent of the target. The monitor state now records `lastAnalysisAt`.
- **Per-source backfill failures**: a source whose ingest step fails after discovery (previously an invisible caught error with `consecutive_failures=0`) raises a daily `backfill_source_failed` alert.
- **Daily refresh fan-out**: the 00:30 Shanghai refresh previously ran all sources serially inside one instance; its subrequest budget ran out partway through the source list and the remaining sources were silently skipped every day (observed: only the first six alphabetical sources ever scanned). Each source now gets its own `refresh-DATE-SOURCE` workflow instance plus a `refresh-DATE-embeddings` instance, and launch failures no longer abort the remaining sources.
- **`/health` alert visibility**: the public health JSON now includes an `alerts` object with open/critical counts (numbers only, never alert text), so any uptime poller can observe incident state.
- **Webhook delivery**: `ALERT_WEBHOOK_URL` (var or secret) delivers alerts as JSON POST alongside email, still gated by `ALERTS_ENABLED`. Per-channel outcomes are recorded in `delivery_status`/`delivery_error`.
- **Analysis retry cap**: `analysis_failed` articles stop being reprocessed after 3 attempts instead of retrying forever; `discovered` articles are never capped.
- **Empty failure reasons**: failure message extraction now falls back through `error.name` to `unknown_error`, eliminating `analysis_failed` rows with `NULL` reasons.

Supporting product changes shipped together: the public read page gained anonymous optional feedback buttons (the preference loop previously had no input path outside the admin UI and had trained on zero samples), and daily ranking applies a date-seeded ±0.3 jitter (`日扰动`) so deterministic scoring plus fatigue penalties cannot lock the winner into a rigid weekly source cycle. Sources `nassim-taleb`, `ted-lamade` and `farnam-street` were paused after data review (6/6, 33/33 and 20/20 analyzed articles rejected by the quality gate with high analysis confidence — a content-bar mismatch, not a calibration bug).

Validation: 186 tests in 27 files (jitter determinism/bounds, windowed health verdicts, webhook delivery/disable, degraded-run assertions, per-source refresh fan-out) plus typecheck and deploy dry-run. AI dependency reliability itself remains the open item: the relay still fails intermittently with `429 usage_limit_reached` and `400 unknown provider for model gpt-5.6-luna`.
